定義した entity

  1. Player — アカウント。Zoo をちょうど 1 つ所有する。
  2. Zoo — プレイヤーの永続コレクション面。
  3. Species — 実在の動物種を表す global master data。
  4. Animal — 捕獲された個体。Species とは別 entity。
  5. Hunter — Guild プールから契約可能な NPC。
  6. HunterContract — Player が現在 Hunter を保持していることを表す。shared-scarce 排他を担保する。
  7. Region — Hunter を派遣可能な場所。
  8. Expedition — Player の Hunter を Region に派遣する time-bounded な割当て。
  9. SeasonalEvent — 出現率・rare-trait rate・Region 状態を期間限定で変更する modifier。

Guild は独立 entity としてまだモデル化しない — 「Guild pool」は Hunter 行の集合として暗黙的に扱い、shared-scarce 制約は HunterContract 側で表現する。将来 multiple guild が必要になれば、Guild テーブルを additively 追加できる。

通貨 G もまだモデル化しない — G に影響する formula が何も決まっていないため、Wallet や ledger は導入しない。これは意図的な欠落であり、後の migration task が「G はもう track されている」と誤解しないよう記録に残す。

関係のハイライト

  • Player 1 : 1 Zoo — unique NOT NULL FK、同一トランザクションで作成される。
  • Species 1 : N Animal — 全 Animal は Species を参照する。
  • Zoo 1 : N Animal かつ zoo_id は nullable — release された Animal は zoo_id = NULL / status = 'released'。
  • Hunter 1 : N HunterContract (履歴上)、ただし active な行は最大 1 つ (ended_at IS NULL)。これが ADR-0002 §7 の shared-scarce Hunter 不変条件。
  • Player + Hunter + Region → Expedition。Expedition は、その Player がその Hunter に対して active な HunterContract を保持している時だけ作成できる。
  • Expedition 1 : N Animal — outcome = 'no_capture' のとき 0 件、outcome = 'capture_success' のとき 1 件以上。
  • SeasonalEvent → Expedition および SeasonalEvent → Animal: 関係は予約するが、Animal 側の provenance 具体 schema は ADR-0002 §18 の未決事項に従い TBD。

schema が守るべき並行性境界

  1. Player → Zoo は 1:1 — Zoo.player_id に unique 制約、Player と Zoo は 1 tx で作成する。
  2. Hunter は active な HunterContract を最大 1 つしか持てない — hunter_id あたり ended_at IS NULL の行が最大 1 行。実装候補: partial unique index、advisory lock、または Hunter 行への SELECT … FOR UPDATE。選択は migration task に委ねるが、不変条件は固定。
  3. Expedition.resolved_at はちょうど 1 回セットされる — resolution は idempotent (ADR-0002 §10)。resolver は Expedition 行をロックし、resolved_at IS NULL を確認し、outcome をサーバ側で決定し、同トランザクションで Animal 行を挿入し、resolved_at と outcome を書いて commit する。
  4. Animal の挿入は解決トランザクションに縛られる — 全 Animal は Animal → Expedition → Hunter と Animal → Species の provenance chain を持つ。
  5. Expedition は active contract に対してのみ作成可能 — 作成 tx は (2) と同じロックを取り、(player_id, hunter_id) に対して ended_at IS NULL の HunterContract があることを確認する。

意図的に TBD としたフィールド

docs/DECISIONS_PENDING.md の全項目はそのまま TBD。ER model 内でも各項目を inline に TBD と明記し、後続の task が placeholder を「確定済み」と誤認しないようにしている。分類:

  • 120 species の正式一覧、Species の code/slug/scientific name、rarity 分類。
  • Region 名 / 数 / difficulty scale / unlock model。
  • Hunter の完全な属性 schema、contract の price/duration/cooldown、Guild availability algorithm。
  • Animal の個体属性 schema (sex, weight, body size, trait catalog, rarity scoring)。
  • Expedition.outcome のより細かい種類 (partial success, injury)、cancellation の可否。
  • SeasonalEvent の内容 / cadence / formula、Animal の event provenance schema。
  • 通貨 G 全体 (Wallet, GLedger, earn/spend rule)。
  • authentication 方式、public player identity。
  • World First の scope、trading policy、anti-abuse policy。

今回の ER model が新たに surface させた open question

docs/DECISIONS_PENDING.md に追記した:

  • HunterContract → Expedition のカーディナリティ (1:1 か 1:N か)。
  • Expedition.outcome — coarse enum のみか、リッチな JSON payload か。
  • Animal.status — 可逆か一方通行か。
  • release 後の Animal 行 — zoo_id = NULL で保持か、削除か。
  • HunterContract.is_active の denormalise の有無 (ended_at IS NULL を唯一の情報源とするか)。
  • SeasonalEvent の識別子 — 数値 code / stable slug / 両方 / 無し。
  • Expedition に hunter_contract_id を直接 FK として持たせるか。
  • 将来 Guild テーブルを導入するか。
  • formula が確定した後、通貨 G subsystem をどう構造化するか。
