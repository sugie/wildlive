The human (repository owner) approved a UI-first prototype covering the entire core loop with dummy data. The instruction was: continue from the Milestone 001 title screen, still with SwiftUI as the main UI framework, and build a walk-through of every screen a player will see — home / own Zoo / other players' Zoos / Guild / contract a Hunter / dispatch to a Region / expedition result / keep-and-name or release / RevenueCat-shaped G purchase — verified in the Simulator without any server communication. The AI proposed the scope (including "no real RevenueCat SDK", "no persistence", "prototype-scaled expedition timers") and the branch ai/013-ios-ui-prototype; the human replied GO.

Objective

Extend Task 008's title screen into a click-through SwiftUI prototype of the WildLive core loop, entirely against in-memory dummy data, so a human can walk through every screen the game will need — home dashboard, Zoo, other Zoos, Guild, contract, dispatch, expedition resolution, capture-and-name or release, and G store — inside the iOS Simulator with no backend involved.

What ships

The app

  • 20 new SwiftUI source files under apps/ios/WildLive/, plus a hand-updated project.pbxproj that adds all of them to the WildLive target.
  • State — AppStore is a single @Observable holding all mutable game state (the current player, other players, hunters, expeditions, contract). No persistence: state is fresh on every launch, deliberately.
  • Navigation — one NavigationStack bound to AppStore.navigationPath. Route is a flat Hashable enum with one case per destination. Every push carries only identifiers, never model instances.
  • Domain + dummy data — Domain.swift defines Species, Animal, Hunter, Region, Expedition, Player, GBundle. SampleData.swift hand-seeds 18 real species, 8 hunters (4 tiers), 6 regions (4 difficulties), 4 G bundles, one current player (with 3 seeded animals), and 3 other players.
  • Services:
    • MockGameService — contract / dispatch / resolve / keepInZoo / release. resolve is idempotent (mirrors the future server transition); a second call returns the already-set state.
    • MockGStoreService implements GStoreServiceProtocol, shaped like a RevenueCat-backed IAP layer. No real RevenueCat SDK is imported. purchase awaits 0.8 s (to exercise the spinner) then credits G to the current player on MainActor.
  • Screens — TitleView (now wired to AppStore.start()), RootView, HomeView, MyZooView, OtherZoosView, VisitZooView, AnimalDetailView, GuildView, RegionPickerView, DispatchConfirmView, ExpeditionsView, ExpeditionResultView, CaptureNameView, GStoreView. Every screen respects safe area, dark theme, and portrait-only.
  • Prototype-scaled timers — expeditions use simulatedDurationSeconds of 8 to 60 seconds instead of the real 10-minute-to-24-hour timings, so a human can play the whole loop inside a Simulator session in under a minute. Real timing lives on the server.
  • apps/ios/README.md updated: Milestone 002 scope, non-goals still in force, CLI build/test commands, and a step-by-step manual playthrough.

Design decisions worth flagging

  • One @Observable store, no DI framework. All screens read from AppStore via @Environment(AppStore.self). This is a deliberate anti-abstraction choice for the UI-first phase: when the real API arrives, only the service layer (MockGameService, MockGStoreService) changes.
  • MockGameService.resolve is idempotent. A second call on a resolved expedition returns the already-set state instead of re-rolling. This mirrors the future server-side transition and matches WildLive's non-negotiable rule that expedition/discovery resolution must be safe to invoke more than once.
  • Prototype-scaled expedition timers (8–60 s). Real durations (10 min to 24 h per docs/GAME_DESIGN.md) would make the loop untestable inside a single Simulator session. The scaled value lives on the client-only Region struct so it is visibly a prototype value, not a design commitment.
  • No RevenueCat SDK. The store screen goes through a GStoreServiceProtocol so a real RevenueCat implementation can slot in later without touching any View. Every UI element (bundle list, spinner, confirmation, error alert) is exercised by the mock.
  • Basic vs. shared Hunters. Only non-basic hunters flip available=false when contracted; basic hunters remain contractable forever. This preserves the "basic hunters never dry up" pillar from docs/GAME_DESIGN.md even in the mock.

Deliberate non-goals (still in force)

  • No REST/GraphQL/WebSocket client, no auth, no user model.
  • No PostgreSQL connection, no pgvector, no server-side code touched. The Task 007 PostgreSQL 17 + pgvector stack was not started for this milestone.
  • No SwiftData / Core Data / UserDefaults persistence. State resets on every launch, intentionally.
  • No real RevenueCat SDK, no App Store Connect product, no receipts.
  • No third-party UI framework, no DI/MVVM/Redux, no analytics, no push notifications, no game engine.
  • No production infrastructure access — nothing sent to any production server, cluster, PgBouncer, DNS, AppRun, or Sakura Cloud. Entire task ran on this Mac.
  • No X manifest (see "Governance" above).

Problems / Known Limitations

  • No automated coverage of the full contract → dispatch → resolve → capture loop. The loop is time-based (up to 60 s per Region) and belongs in a longer manual playthrough, not a fast UI test. The playthrough is documented in apps/ios/README.md.
  • Simulator screenshots of every screen are not committed — Task 008 established the convention of keeping walkthrough screenshots as temporary files that the human reviews in-chat.
  • Expedition timings, capture probabilities, Zoo Value weights, and G bundle amounts are placeholder tuning values, not proposals for the real game economy.
