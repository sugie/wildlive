Entities defined

  1. Player — the account. Owns exactly one Zoo.
  2. Zoo — the player's persistent collection surface.
  3. Species — global master data for a real-world animal species.
  4. Animal — a single captured individual, distinct from Species.
  5. Hunter — an NPC that can be contracted from the shared Guild pool.
  6. HunterContract — represents a Player currently holding a Hunter; enforces shared-scarce exclusivity.
  7. Region — a place a Hunter can be dispatched to.
  8. Expedition — a time-bounded assignment of a Hunter to a Region for a Player.
  9. SeasonalEvent — a bounded-time modifier of appearance rates, rare-trait rates, or Region state.

Guild is not modelled as its own entity yet — the "Guild pool" is the implicit set of Hunter rows and the shared-scarce rule is expressed through HunterContract. A Guild table can be added additively later if multiple guilds are ever needed.

Currency G is not modelled here yet — no G-affecting formula has been decided, so no Wallet or ledger is introduced. Recording that gap is deliberate; a future migration task must not assume G is already tracked.

Relationship highlights

  • Player 1 : 1 Zoo — enforced by a unique NOT NULL FK, created in the same transaction.
  • Species 1 : N Animal — every Animal references a Species.
  • Zoo 1 : N Animal with zoo_id nullable — a released Animal has zoo_id = NULL and status = 'released'.
  • Hunter 1 : N HunterContract historically, but at most one active (ended_at IS NULL). This is the shared-scarce-Hunter invariant from ADR-0002 §7.
  • Player + Hunter + Region → Expedition. An Expedition can only be created when the Player currently holds an active HunterContract for the Hunter.
  • Expedition 1 : N Animal — zero when outcome = 'no_capture', one or more when outcome = 'capture_success'.
  • SeasonalEvent → Expedition and SeasonalEvent → Animal: relationships are reserved, but the concrete provenance schema on Animal is left TBD per ADR-0002 §18.

Concurrency boundaries the schema must protect

  1. Player → Zoo is 1:1 — unique constraint on Zoo.player_id; Player and Zoo are created in one transaction.
  2. Hunter has at most one active HunterContract — at most one row per hunter_id where ended_at IS NULL. Enforcement candidates: partial unique index, advisory lock, or SELECT … FOR UPDATE on the Hunter row. Choice deferred to the migration task; the invariant is fixed.
  3. Expedition.resolved_at is set exactly once — resolution is idempotent (ADR-0002 §10). Resolver locks the Expedition row, checks resolved_at IS NULL, computes the outcome server-side, inserts any Animal rows in the same transaction, then commits.
  4. Animal insertion is bound to the resolving transaction — every Animal has a provenance chain: Animal → Expedition → Hunter and Animal → Species.
  5. Expedition may only be created against an active contract — the creation transaction takes the same lock as (2) and verifies HunterContract for (player_id, hunter_id) with ended_at IS NULL.

Fields deliberately left TBD

Every item in docs/DECISIONS_PENDING.md remains TBD. The ER model calls each one out inline so no follow-up task accidentally treats a placeholder as ratified. Categories:

  • Full 120-species list; Species code/slug/scientific name; rarity taxonomy.
  • Concrete Region names, count, difficulty scale, unlock model.
  • Full Hunter attribute schema; contract price/duration/cooldown; Guild availability algorithm.
  • Per-individual Animal attribute schema (sex, weight, body size, trait catalog, rarity scoring).
  • Finer Expedition.outcome (partial success, injury); cancellation support.
  • SeasonalEvent content, cadence, formulas; the Animal event-provenance schema.
  • The entire G currency subsystem (Wallet, GLedger, earn/spend rules).
  • Authentication method; public player identity.
  • World First mechanic scope; trading policy; anti-abuse policy.

New open questions this ER model surfaced

Appended to docs/DECISIONS_PENDING.md:

  • HunterContract → Expedition cardinality (1:1 or 1:N).
  • Expedition.outcome — coarse enum only, or richer JSON payload.
  • Animal.status — reversible or one-way.
  • Released Animal — row retained with zoo_id = NULL, or deleted.
  • HunterContract.is_active denormalised column vs. ended_at IS NULL as sole truth.
  • SeasonalEvent identity — numeric code, stable slug, both, or neither.
  • Whether Expedition carries a direct hunter_contract_id FK.
  • Whether a Guild table is ever introduced.
  • Currency (G) subsystem shape once formulas land.

Problems / Known Limitations

  • The ER model deliberately leaves many columns unspecified because the game design has not decided them yet. A migration task cannot begin from this document alone — the open questions in docs/DECISIONS_PENDING.md must be resolved first, or the migration task must scope down to only the fields listed as "clearly required" here.
  • No SQL, no PostgreSQL sanity check, no ERD render tool was used — the Mermaid diagram in ER_MODEL.md is checked-in text, not a validated schema.
  • The Animal seasonal-event provenance schema is reserved as a relationship only. The exact column(s) and multiplicity are open because ADR-0002 §18 leaves them open.

What was NOT done

  • No migration, no Eloquent model, no factory, no seeder, no controller, no route.
  • No REST API contract.
  • No JSON schema for Animal.traits or SeasonalEvent payload.
  • No pricing, rarity table, expedition timing table, Zoo Value formula, Visitor formula, or G formula.
  • No authentication choice.
  • No game-fairness balancing.
