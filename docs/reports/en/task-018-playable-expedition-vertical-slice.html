Objective

Turn WildLive from "a real registration slice plus a mocked game" into a genuinely playable first gameplay loop, running on a local stack: iPhone Simulator → SwiftUI → Laravel API → PostgreSQL 17 → persisted game state → back on screen. A human must be able to register, choose an African Map, contract a Hunter, dispatch an expedition, resolve it, keep (and name) or release the animal, and then see it in My Zoo — with every one of those facts stored server-side.

Deliberately excluded: production deployment, Sakura Cloud, RevenueCat, authentication, multiplayer/Guild concurrency, PvP, trading, chat, complete economy balancing, regions other than Africa, and advanced Zoo simulation.

Architecture / Design Decisions

  • One source-to-runtime path for master data — the workbook and the JSON are generated from the same Python literals, so they cannot disagree without that shared source changing first. Documented in RUNTIME_MASTER_DATA.md.
  • Game Master ids as primary keys (map_kenyan_savanna_001) — a row can be traced by eye from spreadsheet cell to API payload without a lookup table.
  • Rules enforced structurally, not by checks that can be forgotten. The Northern White Rhinoceros has no map_animals row, so no code path can produce one. There is no player_hunters table, so a Hunter cannot be owned. rare_find_bonus is referenced in EncounterTable and nowhere else, so it cannot leak into capture success.
  • Injectable randomness — every roll goes through one interface, so no test in the suite can fail on a dice roll.
  • Idempotent transitions — resolution is guarded by resolved_at and the decision by decided_at, both under SELECT … FOR UPDATE, with UNIQUE(zoo_animals.expedition_id) as the structural backstop.
  • Development-only acceleration, impossible to confuse with production — requires an allowed environment, a config flag, and a per-request opt-in; the resulting expedition is permanently flagged in PostgreSQL and in every API response, shows an orange banner in the app, and keeps its real duration in planned_duration_minutes. Canonical expedition_minutes is never modified.
  • Prototype types deleted rather than kept in parallel — the client-side MockGameService, Hunter, Region and Expedition were removed when their server-backed counterparts landed, so there is exactly one answer to "what is a Hunter".
  • Use cases only where they earn it — write flows get an Application use case; read-only screens depend on a Domain protocol directly, per the project's existing "do not create a use case that only forwards" rule.

Problems / Known Limitations

Bugs found and fixed. Four pre-dated this task.

  1. The PHPUnit suite was running against the development database and wiping it. docker-compose.yml exports DB_DATABASE=wildlive into the app container; PHP's CLI copies container environment variables into $_SERVER; and Laravel's env() reads $_SERVER before $_ENV and putenv() — which is all PHPUnit's <env> writes. Harmless while the database held nothing worth losing; in this task it deleted the seeded Game Master data mid-session and broke the running app. Fixed by adding a <server> entry. CI was never affected, which is exactly why it went unnoticed.
  2. The "real API" UI test had been silently skipping. It self-gated on an HTTP reachability ping that runs in the test-runner process, not the app, and never succeeded — so the project's only end-to-end test had stopped testing anything. Replaced with an explicit WILDLIVE_E2E opt-in that fails rather than skips when set.
  3. JSONDecoder.iso8601 rejects Laravel's microsecond timestamps, so every date in every response failed to decode. The client now accepts both spellings.
  4. ExpeditionRejected::$code redeclared Exception::$code as readonly — a PHP fatal error on every refusal path.
  5. AI-introduced regression: the first version of fix #1 forced every DB_* variable, overriding the host and password CI legitimately supplies. CI caught it on the PR; the override was narrowed to the database name alone.

Operational notes.

  • Run the end-to-end tests with -parallel-testing-enabled NO. php artisan serve is single-threaded, and three simultaneous Simulator clones queue behind each other until requests time out.
  • xcodebuild only forwards environment variables prefixed TEST_RUNNER_ into the test process, so the gate is TEST_RUNNER_WILDLIVE_E2E=1.
  • The transaction guards are correct by construction but have not been exercised under real contention — there is no load test.

Values Game Master v0.3 does not fix — chosen for this slice, labelled in ExpeditionBalance and in RUNTIME_MASTER_DATA.md as open questions rather than decisions: the two −8 difficulty penalties, the [5, 95] capture clamp, the 1000 G starting balance, and reading Zoo value as the sum of base_zoo_value without applying Rarity.base_multiplier.
